=== WHAT THIS PROVES ===

1. ★ THE 80B SPRAY IS UNNECESSARY FOR SURVIVAL.
   Freed memory at T1-0x60 (the wrapper-1 slot after GC1) is benign — likely
   all zeros. removeClient reads from T1-0x50 (= freed memory + 0x10),
   sees zeros (mask=0 → 1-slot table, slot[0]=0 → empty), returns without
   writing. deref() decrements rc 3→2. Process survives.

2. ★ NULL-SPRAY IS 100% RELIABLE ON COMPLETED RUNS.
   2/2 runs with redirect survived. Compare to v4f which crashed 1/3.
   v4f's crash (run 2, T1=0x1000b4xxxx) was likely NOT from hostile freed
   memory but from a different cause — possibly 80B spray interference or
   a timing-dependent race. Without the spray, the exploit is simpler and
   more reliable.

3. rc=2 IS STABLE AND PERMANENT.
   - Engine writes rc=3 (one ref() during continuation)
   - GC2 runs deref() once (3→2)
   - Net engine effect: +1 ref - 1 deref = 0
   - rc=2 is our spray seed value. No engine refs remain.
   - fonts.clear() + heavy GC does NOT trigger additional deref()
   - rc stays at 2 from t=3s through t=11s
   - CONCLUSION: The destructor is UNREACHABLE through normal refcount mechanics.
     Nobody will ever call deref() again on this CSSFontFace.

=== IMPLICATIONS FOR EXPLOITATION ===

1. The two-phase UAF can be simplified:
   - Phase 1: UAF 'sa' → spray 192B → read T1 → null +0x58 → GC1 (rc 3→2)
   - Phase 2: UAF 'sb' → spray 192B → read T2, W2 → redirect +0x58 to T1-0x50
              → GC2 → rc 3→2 → survive
   - NO 80B spray needed. Simpler, faster, more reliable.

2. The two-phase UAF gives:
   - Two 192B buffers (lane1[hit1], lane2[hit2]) with full JS read/write
   - Four leaked heap addresses (T1, W1, T2, W2)
   - T1/T2 are in the 80B heap region (hash table addresses)
   - W1/W2 are in a different region (WeakPtrImpl addresses)
   - Neither contains code pointers

3. HARD BLOCKERS remain:
   - WebProcess text base unknown (no ASLR defeat path)
   - Heap NX enforced (no JIT)
   - Destructor unreachable (rc=2, no refs)
   - Buffer absolute VA unknown (can't self-reference)
   - iterateClients unreachable from JS (walk arm dead)

4. The TWO-PHASE redirect works as a CONTROLLED READ oracle:
   - removeClient reads 8 qwords from whatever +0x58 points to
   - If we point +0x58 at different freed 80B slots, removeClient reads them
   - But we can't OBSERVE what removeClient read (no return value)
   - The only observable is: survive (data was benign) vs crash (data was hostile)
