# Handler 657: batched memory commands

## Identity and evidence boundary

The supplied 4096-byte `handler_657.bin` is a trampoline window, not a standalone implementation. Its first instruction at RVA `0x265f78` branches to `0x9a9f40`; sysent records 4 argument slots. Source bytes were verified against `kernel_text.bin` at matching RVAs. Runtime VA is recorded base `0xffffffff8a9c0000` plus RVA. Raw SHA-256: `7d576be693fd7630d871724e32c49d9e9c8e53c01957cd07d432e840f6255c1a`. Prepared forward target slice SHA-256: `33f23b2ee0ba62c0453e47294e249e0566cd2f6a386eed64e8c4b8aae031a6c5` (16,384 bytes).

REA 6.7.0 with Ghidra 12.1.4 supplied actual function-aware assembly and pseudocode. Body carriers: `handler_657.body.dossiers.jsonl.gz`, `handlers_b.copy_support.dossiers.jsonl.gz`. ## Functionality and dispatch

Observed: the target at `0x9a9f40` accepts a user record pointer, signed 32-bit count, optional processed-count output pointer and 32-bit flags. Nonzero flags or a negative count returns `0x16`; zero records succeeds. It copies the first `0x20` bytes through `0x259280`, obtains `td->proc->map` through offsets `+8,+0x200`, and performs a map lookup using the record's qword at `+8`. It requires a successful lookup, entry flag `+0x60 &2` clear, a nonnull `+0x50` object and object byte `+0x9d ==11` before dispatch (`0x9aa02a..0x9aa08c`). Evidence: `ev_8b7aa19c6f28267cdcee0d8eac6492d5c6a1207c5f01c4041040eb1005ecd217`.

The opcode is the first 32-bit field. Values1..5 index signed relative table `0x18cdb30`; the table itself is outside supplied text/data. Invalid opcodes return `0x2d`. Five visible landing pads call `0x9aa250`, `0x9ab160`, `0x9aa860`, `0x9aa8d0` and `0x9aa380` (`0x9aa0d4..0x9aa15f`). The exact opcode-to-pad mapping is unresolved. The REA entry pseudocode incorrectly stops at the unresolvable computed dispatch and therefore omits substantial loop/cleanup code visible in the assembly. Treat its apparent indirect-call return as a recovery limitation, not runtime behavior.

Observed: `0x9aa250` rejects nonzero record+4, requires address and length aligned to `0x10000`, checks containment using subtraction against lookup bounds and rejects protection bits outside `0x33` (`0x9aa261..0x9aa2bc`). Memory-type policy includes process fields and downstream checks, so this is a memory management command interface rather than arbitrary unbounded byte access. Evidence: `ev_747fad2e57d10789f44c61590316037646abcbf92c9696fa8bb0c039f4e58c82`. Helpers `0x9aa380` and `0x9aa8d0` process further records through passed cursor/end pointers; those pointer updates explain why the entry counts consumed32-byte records rather than simply incrementing a scalar once per call. Evidence: `ev_581e2217d83757fdbd3f80a6f4ce7e563271fb02c8a5bd6d475c156a0c70a1cd`, `ev_64ea9a7a212d6a383a464ec3c7a2aaabe5c375c7cf85c7f638818d22edb3c59c`. Names such as `bplbuf`, `bplful`, `bplrng` and `bplflsh` are observed local rodata references; exact public API naming remains unproven.

## Dataflow, checks and attack surface

The range boundary is computed as `commands + (signed_count <<5)` (`0x9aa08d..0x9aa09b`); all records are copied separately and helper functions can consume additional records. On an error the cursor is rewound one record (`0x9aa22e`) before publishing the processed count using `0x259790` (`0x9a9f7a..0x9a9f87`). That helper's return is ignored. On completion/error the entry clears byte `td+0x117` if set, invokes an indirect map callback after an address-range check and releases the map (`0x9aa1c8..0x9aa21e`).

The user controls counts, record bytes and output pointer; relevant review boundaries are cursor arithmetic, helper multi-record consumption, copied-record validation, partial progress reporting and memory-object lifetime under map locking. Visible object/range/protection checks establish local constraints. The meanings of external helpers, credentials/capabilities and mutable policy remain unknown; this report makes no global permission or exploitability claim. Later storage routines in the 16KB context, including diagnostic references to `m2storage_*`, are adjacent code and are not attributed to this syscall.

## Shared user-copy evidence

Supporting REA records confirm `0x2591d0` copies kernel bytes to user memory, installs/clears a fault-recovery pointer and for nonzero length rejects unsigned pointer+length carry, end addresses above `0x800000000000` and nonzero process byte+0x591. Evidence: `ev_71486184be245b984abbb9be576981c38f613a7db64a834e00ab1b4e60ea2113`. `0x258ff0` is a byte-counted zero-fill implementation, not copyout: `ev_9f715f53ca8e7945dcf5dd090a09697d620766198f5ec9c1ad147fd5676b3ea0`. The source-copy helper `0x259280` validates the user source range and includes fault-recovery state, but its narrow support carrier cuts control flow at the fault/return region; its REA `halt_baddata` is a coverage limitation and is not treated as a real normal-path halt. Evidence: `ev_5d07d221cf60ecec155e82677b4906065788d1c1d1f1444ffffeccc565bd92ad`. These helpers' local address checks do not establish broader syscall authorization policy.


## Coverage, limitations and artifacts

`.rea.asm` contains the original raw window's 512 recovered trampoline functions with individually attributed REA assembly and verified padding, the recovered body/helper functions, and clearly labeled GNU objdump disassembly of all 4096 original bytes. `.rea.c` contains analyst ABI views and readable entry behavior followed by unchanged actual REA pseudocode, including the original entry. All recovered carrier functions are retained. Prologue-pattern seeds are analysis candidates rather than proof of original ABI boundaries; unusually short or end-clipped entries may be fragments, and unresolved computed flows can hide additional blocks. Spatially adjacent functions must not be treated as reachable from this syscall without a direct edge or supporting branch evidence.

The raw-entry and target evidence IDs are `ev_da7f3ede978ec0f8913a8bc6ab90ee670e3f279fdce9453c39d875b397f798b4` and `ev_8b7aa19c6f28267cdcee0d8eac6492d5c6a1207c5f01c4041040eb1005ecd217`. Supplemental literal extraction is in `handler_rea_evidence/handler_657.rodata.json` (`local-rodata-handler-657`, explicitly not a REA record); mapping is kernel_data.bin file+0 to RVA0x1000000. Function-level limitations remain in the C comments and retained dossiers. No kernel code was executed. The raw-entry decompiler may show `halt_baddata()` for an external tail jump because its destination lies outside the raw carrier. That warning is a recovery artifact: the verified machine instruction is an unconditional JMP to the separately recovered target. Static calls do not prove runtime reachability or exploitability. External authorization, global tables, mutable state and full subsystem policy are unresolved where not supplied. Types and semantic names are analyst recovery unless established by a referenced literal.
