## Behavior and data flow

Copies a name with bound 0x20 and looks up `(name, 0x120)` in the shared registry. On success increments object shared references at +0x54, releases the registry lookup context, reserves a caller-local handle, and publishes it. Success returns the handle via `td + 0x408`. Missing name/object returns 3. Handle reservation failure returns 0x23 and undoes the shared reference under registry context; zero remaining references frees name/object.

## Dispatch and subcommands

No user-selected function table or selector switch in the entry. The related type-0x120 operations are create 549, delete 550, open 551, close 552, wait 553, poll/try-wait 554, post/signal 555 and cancel/reset 556. Names describe recovered behavior and are not original symbols.

## Permission checks and validation

No direct credential predicate appears. The name copy is bounded and the lookup supplies type 0x120. Name visibility and ownership policy are delegated to the shared registry; the entry does not compare caller UID to creator PID.

## Attack surface and limits of conclusions

Cross-process naming and reference lifetime require registry analysis. The reference increment is immediately followed by a registry-context release call, so it must not be classified as an unprotected increment without checking that contract. Handle-allocation rollback is explicit.

This is static analysis of a recorded kernel image. A missing check in this body does not establish that the syscall entry path, object namespace, or external callees impose no checks. Review points are not confirmed vulnerabilities or exploit primitives. No target code was executed.
