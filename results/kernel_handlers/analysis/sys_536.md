## Behavior and data flow

The entry at `0x4f6a70` reads PID, an opaque eight-byte module handle and a user output pointer. It resolves/holds the process with `sub_004f6700`, checks process state through `0x9fcf00`, and returns `0x23` for the observed incompatible state combination (`result != 2` and `(state & ~1) == 2`). It then calls `sub_004f6b70(td, process, 1, handle, output)` and releases the process. The query helper locks the loader context, locates the module by its +0x28 handle, creates a zero-initialized `0xa58`-byte information record, copies a bounded module name, and fills module/process fields. Its extra work includes looking up image information and reading metadata, with different paths for the caller’s process and another process. Missing loader context returns `0x2d`; no matching handle returns `0x16`. Full recovered helper pseudocode is included to retain all output-population branches.

## Dispatch and subcommands

No user selector dispatch in this entry: the wrapper fixes the helper’s mode argument to 1. Branches in the shared helper depend on module flags and metadata versions; they are not separate syscall subcommands.

## Permission checks and validation

Same three-way OR credential gate as 535: `0x609020` via trampoline `0x26d0a8`, `0x609040`, `0x609110`; denial returns 1 before process access. The shared process lookup rejects restricted target credentials/process flags and holds the process. Loader data is traversed under a loader lock. Output pointers go through copyout-like routines; record initialization is explicit.

Recovered predicate bodies make the entry whitelist concrete: `0x609020` compares credential qword +0x58 to **0x4800000000010003**, `0x609040` to **0x4800000000000006**, and `0x609110` to **0x4800000000000007**. These are identity-value checks, not a UID-zero test. The first is reached through the verified trampoline at 0x26d0a8. Original policy names remain unavailable.

## Attack surface and limits of conclusions

Review output structure pointer-valued members and address-bearing module information for intended disclosure; an address-bearing record is not by itself a kernel-address leak. Cross-process reads and module lifetime are the principal boundaries. The helper’s references to external routines and unmapped data limit naming of every record field. No arbitrary write or missing entry credential check is established.

This is static analysis of a recorded kernel image. A missing check in this body does not establish that the syscall entry path, object namespace, or external callees impose no checks. Review points are not confirmed vulnerabilities or exploit primitives. No target code was executed.
