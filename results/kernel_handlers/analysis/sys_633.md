## Behavior and observed layouts

Body `0xffffffff8adf9070`–`0xffffffff8adf9142` is a companion to 632: one u64 ID, equality with sign-extended caller `+0x9c` returns 22, and `0xffffffff8b552420(ID, u32(*(caller+8)+0xbc))` must return a target (otherwise 3). Target fields are pointers `+0/+8`, u32 flags `+0xe4/+0xe8`, state u32 `+0x400`. It calls `0xffffffff8ae878b0(target,0,0xffffffff8bcd1b07,0x36c)` before mutation.

If signed `+0xe4` is negative, it clears the sign bit (`&= 0x7fffffff`) and succeeds. Otherwise `+0xe8 & 0x20` must be set: clear that bit; only when the entire resulting `+0xe8` word equals zero does it set state `+0x400=2`; then call `0xffffffff8b5c6b20(target)` and succeed. If neither condition holds, return 22. All acquired-target paths call the same two release-like helpers seen in 632, with `*(target+0)+0x18` and `*(target+8)+0x148`.

## Restrictions, returns and surface

No selector dispatch or caller-buffer copies occur. Visible restrictions are self-ID rejection, scoped lookup and state bits; authority checks may reside in the opaque lookup. Numeric returns are 0, 3 and 22. A resume/wakeup-like counterpart to 632 is inferred from clearing its bits and invoking the helper; no concrete function name is asserted. State word transitions and object lifetime across these helpers require further callee review. No vulnerability is proven.
