# Native syscalls 726/727: the AIO debug pointer disclosure (13.60)

Two handled syscalls in the 13.60 image hand **raw kernel pointers** to userland. They sit in
the native 735-entry sysent table and are absent from the 677-entry table the 14.10 console
dispatches through, so they are a static result, not a live primitive. This document records
what they are, exactly what they copy, and why the 14.10 target cannot reach them.

## Identity

| number | name | thunk RVA | body RVA | reference |
|---|---|---|---|---|
| 726 | `get_aio_debug_submit_info` | `0x265750` | `0x3b2d50` | `docs/sysent-names-13.60.csv:726` |
| 727 | `get_aio_debug_request_info` | `0x265758` | `0x3b3090` | `docs/sysent-names-13.60.csv:727` |

Both thunks are plain `jmp rel32` stubs inside the veneer farm
(`results/kernel_handlers/asm/sys_662.asm`, trampoline window at file offset zero = RVA
`0x265718`): `0x265750: JMP 0x003b2d50`, `0x265758: JMP 0x003b3090`. Bodies are carried in
`results/kernel_handlers/decompiled/sys_669_deep.c` — 726 at lines 625-720, 727 at lines
765-885 — because the 669 carrier window reaches them.

Neither number appears in the 679-line compat capture (`docs/sysent-compat-names-13.60.csv`,
677 entries, ELF32/FreeBSD32 ABI). That absence is what produced the handoff's open item: an
unnumbered handler next to 670. It was a table mismatch, not a missing syscall.

## Why the compat capture could not have named them

The 679-entry `sysent_index.json` is the compat table. Its extent is 677 entries:
`sysent_area.bin` inner offset `0x1000 + 677*48 = 0x8EF0` is the head of an adjacent
16-byte `(data_ptr, text_ptr)` pair table — pairs `(0xffffffff8c497e58, 0xffffffff8ac1dc28)`
and `(0xffffffff8c497e88, 0xffffffff8ac1dc30)`. The capture's "entries" 677 and 678 are those
pairs, which is why their `narg` fields read `2353626712`/`2353626808`.

The native table lives at RVA `0xe76e50`, stride 48, 735 entries, and ends at `0xe7f820`
(loop bound `cmp r13,0x2df` at `0xa5e560`). Its tail is what names 726/727; entries 551-734
lie outside the captured 64 KiB file.

## 727 — `get_aio_debug_request_info`

The handler is called with `(struct thread *td, uint32_t *uap)`:

    +0x00  u32  handle        per-process handle table, class 0x15 (AIO context)
    +0x08  u32  flags         low 16 bits: record flag word to match
                              high 16 bits: start index, must be <= 0x7f
    +0x10  u64  dest          user buffer, 24 bytes per returned record
    +0x18  u32  count         record slots requested
    +0x20  u64  count_out     user u32, receives the number of records written

Flow (`sys_669_deep.c:765-885`):

1. `dest == 0 || count_out == 0` -> return `0xe` (EFAULT).
2. `func_0x0053c260(handle, 0x15, &local_50)` resolves the AIO context; `func_0x005a8110`
   references it; a failed reference or a null `*(long *)(local_50 + 0xc48)` returns `3`.
3. `count < 1 || *(int *)(ctx + 0x228) < count` -> return `0x16` (EINVAL).
4. `start = flags >> 16`; `start > 0x7f` -> return `3`.
5. `malloc(count * 0x18)`, then walk the request array `[[lVar11+0x28] + start*8]` and, for
   each of `**(int **)(record + 0x20)` populated entries, copy three fields out of the
   kernel structure at stride `0x28`:

        out[i].+0x00 = u32  [base + 0x20 + (start+i)*0x28]
        out[i].+0x08 = u64  [base + 0x08 + (start+i)*0x28]   <-- kernel pointer
        out[i].+0x10 = u64  [base + 0x00 + (start+i)*0x28]   <-- kernel pointer

6. `sub_003b3a40(&local_3c, count_out, 4)` copies the record count out, then
   `sub_003b3a40(buffer, dest, local_3c * 0x18)` copies the records.

The write loop is bounded by `count` and the copy is guarded by `local_3c <= count`, so the
only defect in this path is the disclosure itself: two 64-bit kernel addresses per record,
readable by anyone holding an AIO context handle. On 13.60 that is a complete KASLR defeat
plus a read of AIO bookkeeping state; with a second, unrelated bug that lets the start index
or the stride be steered, it becomes a read of arbitrary kernel memory at stride `0x28`.

## 726 — `get_aio_debug_submit_info`

Same shape with a different uap and 16-byte records:

    +0x00 u32 handle   +0x08 u64 dest   +0x10 u32 count   +0x18 u64 count_out

Records are four dwords — `{queue id | slot << 16, request word [0xe], context word, request
word 0}` — with no kernel pointers, so 726 is information about the submit queue only. The
count bound is `ctx + 0x228` again, the same `0x7f` start index does **not** apply (726 has
no flags word), and the scan walks `ctx+0x220` queues of 128 slots.

## Reachability on 14.10: none

Three measurements fix the live dispatch table on the target:

* `sys 677` (`wait6`) and `sys 678` (`cap_rights_limit`) kill the process **and** panic the
  console. A present handler cannot panic on argument values — bad user pointers come back
  through the fault-recovering copyin/copyout helpers. An index past the end that lands in
  the pair table above jumps to a text pointer used as a `sy_call` and faults in kernel mode,
  which does panic.
* `docs/SYSCALL_ABSENT_VS_LETHAL.md` established that an absent slot terminates the caller
  instead of returning `ENOSYS`.
* Every number the corpus can account for below 677 answers, and 662 answers *correctly*:
  `probes/phase17_new_vectors/486a_aio662_gate.lua` measured `count = 1, 4, 16, 128 -> 0`
  and `count = 129 -> -1`.

So the live table on 14.10 ends at 677 entries, and 726/727 (native tail) are outside it. The
seventeen native entries from 677 to 734 — `wait6`-adjacent debug, `apr_*`, `get_phys_page_size`,
`fsc2h_ctrl`, `streamwrite`, `app_save`, `ioreq`, `dynlib_get_lid_mid_info`, `mmap2`,
`get_aio_debug_*`, `virtual_query_by_pid`, `fgcinfo_*`, `cffmgr_call`, `trace_ctrl` — are gone
on the target. No probe should be written for them; a call costs a console panic and can only
reproduce the panic already measured at 677.

The remaining question is static, not live: whether 14.10 keeps the *bodies* (726/727) and
reaches them through a different index. Answering it needs a 14.10 kernel dump, which the
project does not have. Nothing in the 13.60 corpus ties either body to a second thunk.

## What this changes in the corpus

* Objective "find the number of `sub_003b3090`" is closed: 727, with 726 as its sibling.
* The corpus has no reachable kernel-pointer disclosure for the 14.10 credential: the AIO
  family's user-visible output is 4-byte status words only (`docs/HANDLER_CLAIM_CORRECTIONS.md`
  section 7), and the two calls that do export pointers are out of range.
