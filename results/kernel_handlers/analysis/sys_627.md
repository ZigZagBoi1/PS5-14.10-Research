# Handler 627: static REA review

## Provenance and scope

- Original input: `handler_627.bin`, exactly 4096 bytes; SHA-256 `cf4ec20a234b0ab3de686b8d08015bc451e27a111f44fc360cd42fde80a92bc0`. The input is 512 independent 8-byte trampolines, with only offset zero representing this requested syscall.
- Trampoline runtime VA `0xffffffff8ac25ec0`, kernel RVA `0x265ec0`, narg=2; jump target `0xffffffff8ae62850` (RVA `0x4a2850`).
- Supplemental root bytes reviewed: `[0xffffffff8ae62850, 0xffffffff8ae62cd6)`, obtained from supplied kernel_text through the analyst ELF at original base `0xffffffff8a9c0000`. They are separate from the original input window; analyst metadata and names are synthetic.
- Static instruction/dataflow review only. REA root export is tracked in `rea_616_645_evidence/function_ffffffff8ae62850.json`; no live kernel execution or exploit validation is claimed.

## Permission gate and interface

This root requires bit62 of the qword at `*(td+0x140)+0x60`, corroborated by independent helper bytes at kernel_text RVA 0x608f90. Unlike handlers 618/623, a clear bit returns **0x4e**, not 1. Accepted callers first execute synchronization helper **0xffffffff8ae62ce0**, even for a count-only request.

Arguments are user record-array pointer +0 and user count pointer +8. A NULL array selects count-only mode. A non-NULL array fetches signed count32 through **0xffffffff8b142a40(user_count)**: -1 becomes **14**, any other <=0 becomes **22**, positive count forms array capacity=count*0x28 bytes. No command switch or indirect selector dispatch appears in this root.

## Count-only and snapshot paths

Count-only locks **0xffffffff8df49e60** with `0xffffffff8b60b350`, traverses process-like list at head **0xffffffff8df49e80** following each +0 link, and under each process+0x148 lock adds signed count32 at process+0xb48 into a 32-bit total. It does **not** apply the process-state test used in snapshot mode. It unlocks the list and writes the total using **0xffffffff8ac19790(user_count,total)**; nonzero becomes 14.

Snapshot mode builds iov/uio-like objects for user array and positive count*40. Under the same global list lock it visits each process. It takes process+0x148 and skips any whose state32 at +0xb8 !=1. Otherwise it snapshots count+0xb48, releases the process lock, allocates count*40 bytes using **0xffffffff8b5c8b50(size,0xffffffff8c488120,0x102)**, reacquires, and retries allocation if the count grew. This retry also rechecks state. It additionally locks process+0x168 while traversing thread-like list at process+0x10 following thread+0x10. Each thread uses `0xffffffff8ae878b0(thread,0,0xffffffff8bc6a1cd,0x647)` and corresponding release `0xffffffff8ae87520(*(thread+0)+0x18,0,0,0)`.

Exact output stride is **0x28**:

| Output offset | Source / operation |
|---|---|
| +0x00 uint32 | Process+0xbc |
| +0x04 uint32 | Thread+0x9c |
| +0x08,+0x10 int64 pair | First 16 bytes from helper 0xffffffff8ae61a20(thread,local_usage), unless special flag |
| +0x18,+0x20 int64 pair | Next 16 bytes from that helper, unless special flag |

When byte thread+0xed has bit2 (0x04), the first pair is zero; it calls **0xffffffff8b4909c0(qword at thread+0x238)**, divides its signed64 result by **1,000,000**, and writes quotient/remainder to the second pair. The unit/name of the timing data is not proved by the root. The constant and signed arithmetic are directly observed.

After each process snapshot it releases process/thread-list locks, transfers `min_unsigned(allocated_bytes,uio.residual)` via **0xffffffff8b142520**, truncating this byte count to uint32 at the call, and frees. The transfer can be partial and the traversal/counting continues after residual capacity is exhausted. The output count is a 32-bit number of threads enumerated across eligible processes, even when the user array was smaller. If a per-process count shrank after allocation, the requested transfer size still uses the allocation count, not the actual per-process number visited. Whether spare bytes are guaranteed zero depends on allocator flags/invariants, which are not assigned semantics here.

Transfer errors propagate after free and global unlock. On success the global lock is released and the total enumerated thread count is written to user+8; write failure becomes 14. Count-only sums all process counts while snapshot enumerates only state1 processes, a visible distinction that may affect concurrency/interpretation.

## Synchronization helper and side effects

The nearby helper **0xffffffff8ae62ce0..0xffffffff8ae62dd1** is also byte-reviewed. It locks **0xffffffff8def6578**, clears qword **0xffffffff8def6528**, increments current_td+0x5a8 atomically, calls `0xffffffff8b077940`, loops CPU IDs through global max **0xffffffff8e6ce8b8**, tests online-mask qword **0xffffffff8e6ce8e8**, builds a required bitmap and atomically ORs the current-CPU bit into the shared completion mask. It calls **0xffffffff8b1de5b0(8)**, then **0xffffffff8b077960**, atomically decrements td+0x5a8 and conditionally calls **0xffffffff8b077af0** when the prior value was 0x80000001. It spins with PAUSE until shared mask equals the required bitmap, then unlocks. Cross-CPU synchronization is a strong inference; callback/event registration and precise interrupt/critical-section semantics remain unknown.

The timing helper **0xffffffff8ae61a20** also updates accounting-like thread/process fields. For current thread it samples an indirect callback and updates thread+0x238/+0x230, then folds thread counters into process+0x2c0..0x2d8 and thread+0x1f8..0x210 before clearing transient counters. Its final formatter is another helper. Therefore enumeration has accounting/synchronization side effects; it is not a pure memory dump.

## Errors and attack surface

Visible statuses are 78 for credential-bit denial, 14 for count fetch/store failures, 22 for nonpositive capacity, and propagated transfer status. Stack-protector mismatch calls **0xffffffff8b0bd6b0** then UD2. The root writes no syscall-return slot.

Caller-controlled count/output addresses are checked partly in root and partly by memory-transfer helpers. Allocations and retry loops depend on process/thread count invariants; the global-list lock stays held across allocation/snapshot/copy stages. Count multiplication uses 64-bit arithmetic for the positive user capacity, while transfer length truncates to uint32 per process. Potential padding exposure, count races, or resource-cost consequences require allocator and helper guarantees; no vulnerability is asserted from these observations alone. The fixed synchronization wait can only be assessed with the missing callback/CPU-mask invariants.
