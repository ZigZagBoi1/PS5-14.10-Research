# Handler 618: static REA review

## Provenance and scope

- Original input: `handler_618.bin`, exactly 4096 bytes; SHA-256 `e3d7f6a46a44c1fe9f67d2c5cf63afddb572609de492e50239790b7d7f88fb31`. It contains 512 independent 8-byte trampolines. Only offset zero belongs to the requested syscall.
- Requested trampoline: runtime VA `0xffffffff8ac25e80`, original kernel RVA `0x265e80`; narg=3. Its jump target is `0xffffffff8b47d0f0` (RVA `0xabd0f0`).
- Supplemental body reviewed: `[0xffffffff8b47d0f0, 0xffffffff8b47d424)`, from supplied `kernel_text.bin` via analyst ELF. Original runtime base is `0xffffffff8a9c0000`; analyst ELF metadata/labels are synthetic. The target body is not inside the original input window.
- Review basis: static instruction/dataflow inspection of unchanged source bytes. REA root export is tracked in `rea_616_645_evidence/function_ffffffff8b47d0f0.json`; decompiler output is not substituted for byte-level evidence. No live kernel execution or dynamic security claim is made.

## Behavior and recovered layouts

This root snapshots a global linked list into records with exact stride **0x128**. It requires bit 62 of the qword at `*(td+0x140)+0x60`; the helper `0xffffffff8afc8f90` was independently checked at kernel_text RVA 0x608f90. Failure returns 1 before reading list state or copying output.

Arguments: user buffer pointer +0, signed 32-bit byte capacity +8, optional user total-size pointer +0x10. The root builds an iov-like object `{base,length}` and a 0x30-byte uio-like object: iov pointer +0, iov count32 +8=1, offset64 +0x10=0, residual64 +0x18=sign-extended capacity, two words +0x20/+0x24=0, thread pointer +0x28. These names describe observed usage and offsets.

It locks `0xffffffff8dede060`, counts all nodes from head `0xffffffff8dede038` following +0x20, unlocks, allocates count*0x128 using `0xffffffff8b5c8b50(size,0xffffffff8d5bc080,0x102)`, then reacquires the list lock. Each node is protected through calls on node+0x18. Nodes with flags32 at +0xa0 bit 3 set are skipped. For a candidate it checks the allocation count before filling a record; if the list grew beyond allocation capacity, it unlocks, frees, and restarts the count/allocate pass.

Output layout: qwords +0/+8 from node+0x130/+0x138; qword +0x10 from node+0x88; sign-extended int32 +0x18 from node+0xa8; dword +0x20 from node+0x148; kind byte +0x24; byte +0x25 from node+0x151; optional string region at +0x26, bounded to 0xff bytes. The stride leaves three bytes after that region. Allocator flag meaning/initialization is not established here; padding/string-tail leakage cannot be concluded without it.

## Dispatch and coverage boundary

The unsigned selector byte at node+0x9d is checked against 8 at `0xffffffff8b47d2b2`; values above 8 skip the node. Values 0..8 index a signed relative-offset table at **0xffffffff8c29bf68**. Those table bytes are outside all supplied text/data coverage. Numeric selector-to-block assignments are therefore **unknown** and are not invented in semantic C.

## Output, errors, and attack surface

After unlocking, `0xffffffff8b142520(records,min_unsigned(sign_extended_capacity,count*0x128),&uio)` transfers bytes, then allocation is freed. A nonzero transfer result propagates. On success and non-NULL args+0x10, `0xffffffff8ac19720(user_size,count*0x128)` writes the full required size; any nonzero result becomes 14. Otherwise return 0. The signed input capacity is not explicitly rejected when negative; its comparison is unsigned, while uio residual remains sign-extended. Exact transfer-helper validation is needed before treating that as a bug.

The surface is global object metadata enumeration with caller-controlled output addresses/capacity. Allocation count multiplication and list growth retries depend on list invariants. Per-node locking and count retry are visible; allocator failure conventions, name-helper validity, table contents, and transfer-helper behavior beyond its call are unresolved. No exploit or memory-corruption condition is established by this static root alone.

## REA evidence and reconciliation

Ghidra 12.1.4 dossier evidence ID: **`ev_2c4804e5fd7301f6df7e7cdc1eda231eeaae0dbace310e1d11fbdfe54fe64f4e`**. Subject SHA-256: `30067e73763adb1a8b061f29e80bf32a7c61e8261ed98ed8b4f221a4ecc18d0f`. Normalized procedure body has 631 bytes across inclusive range(s) `0xffffffff8b47d0f0..0xffffffff8b47d20c`, `0xffffffff8b47d261..0xffffffff8b47d2d6`, `0xffffffff8b47d340..0xffffffff8b47d423`. The normalized pseudocode and instruction listing were reviewed against the supplemental raw disassembly.

Ghidra reports an unresolved indirect jump and treats it as a call because the relative-offset table is unmapped. Its body address-set excludes the branch blocks behind that jump. Those blocks were separately recovered from the unchanged supplied target-context bytes and are described above by address; their selector mapping stays unknown. In particular, decompiler apparent zero record count/zero output size is an artifact of the missing emitting blocks, not proof of a zero-length enumeration. The manual semantic recovery preserves the missing-table boundary explicitly.

Empty normalized callee lists do not mean no calls: unresolved call targets outside the selected ELF context still appear as address-labelled calls in the assembly. Independent helper observations explicitly identified above come from `kernel_text.bin`, SHA-256 `406ab210236d4123e06495bcc8da82d8f89dac07266558dc8c0f80cc6cf55cf1`, and are supplemental byte analysis rather than claims of REA-provided symbols.
