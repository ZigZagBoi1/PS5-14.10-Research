## Behavior and recovered fields

This zero-argument root derives a page boundary from current thread state. It loads process=`*(td+8)`, map-like pointer=`*(process+0x200)`, frame-like pointer=`*(td+0x460)`, and saved address=`*(frame+0x100)`. It calculates `(saved_address-0x80) & ~0x3fff`, retaining 16KB alignment and unsigned subtraction semantics.

It calls `0xffffffff8ac86820(map,0,0)`, then `0xffffffff8ac86c40(map,address,&entry)`. A nonzero lookup result leads to `pages=(address-entry->field_20)>>14`. Only when the low32 pages interpreted as signed is positive does it call `0xffffffff8ae23610(entry->field_50, arithmetic_shift(entry->field_58,14), pages&0x7fffffff,5)`. The fields at entry+0x50 and +0x58 are pointer64 and signed offset64; entry+0x20 is a base-like address64. It finishes with `0xffffffff8ac86870(map,0,0)` and returns 0 regardless of lookup result or the operation's result.

The paired map calls are lock/unlock-shaped, and the derived address and object range suggest a virtual-memory action beneath the saved stack address. Exact VM operation, allocation/map type, saved-register identity, and mode 5 meaning are inferences/unknowns, not named APIs.

## Errors and attack surface

There are no syscall arguments, command dispatch, user buffer copies, explicit credential predicates, or return-slot writes. Local errors are suppressed: both failed lookup and nonpositive page count return 0; any status from the range operation is not examined. Stack protector failure invokes `0xffffffff8b0bd6b0` followed by UD2.

Caller influence is indirect through saved execution context and existing address-space state. The root confines itself to the current process's map-like object, but helper-body semantics are needed to establish object lifetime, lock requirements, exact range bounds, and the effect of mode 5. It is not evidence of an arbitrary-address primitive.
