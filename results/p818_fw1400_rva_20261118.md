## Methodology

The 14.10 RVA was found by scanning for ELF magic (`7f454c46`). This fails on 14.00 because the ELF header page sits in `.text`, which the PS5 hypervisor maps as **execute-only** via EPT — any read attempt kills WebProcess with SIGBUS (not a catchable JS exception).

### Boundary scan approach

Instead of reading the ELF header, we locate the **.rodata → .text boundary**:

1. **Coarse scan** (256 KB steps): Read pages starting from VP downward. `.rodata` near VP is readable; `.text` below it is execute-only. Step downward in 256 KB (`0x40000`) increments until a read crashes WebProcess.
2. **Fine scan** (16 KB steps): After a coarse crash at delta D, refine with 16 KB (`0x4000`) steps to find the exact page boundary.
3. **Distance extraction**: The first execute-only page marks the top of `.text`. `distance = VP - crash_page` is pinned to 16 KB by the fine scan. The trailing `0xB28` is VP's page offset (observed identically in all 16 slides and on 13.60), not a measured sub-page quantity — the scan cannot resolve below 16 KB.

### Precision note

The fine scan steps at 16 KB (`0x4000`). The byte-precise `0x7F00B28` combines two values:
- `0x7F00000`: the 16 KB–aligned distance from the fine scan [M]
- `0xB28`: VP's known page offset, constant across all slides [M]

The resulting RVA is pinned to 16 KB (not 4 KB). A 4 KB–aligned base in a different position within the same 16 KB window would give a different RVA, but no such position has been observed.

### Crash recovery

Each crash kills WebProcess; the PS5 browser reloads the page with a new ASLR slide. State survives via server-side JSON (VP-relative deltas, not absolute addresses). Sub-phase routing uses bit-encoding in the delta value itself (bit 0 set = fine scan), requiring no server restart.

## Ambiguity: image offset of .text

The claim `base = first execute-only page` holds only if `.text` begins at image offset 0. Two layouts are possible:

**Layout A** — `.text` at image offset 0 (base = first exec-only page):
```
base ────── page 0     [X]  .text starts here
             page 1     [X]  .text
             ...
             page N     [RW] .rodata starts here
             ...
VP ──────── page N+M         .rodata (CSSFontFaceSet vtable)
```
RVA = `0x7F00B28`

**Layout B** — ELF header at image offset 0, `.text` at offset `0x1000`:
```
base ────── page 0     [RX or RW]  ELF header (not in .text)
             page 1     [X]        .text starts here  ← first exec-only page
             ...
```
RVA = `0x7F01B28` (base is `0x1000` below the first exec-only page)

On 14.10, the ELF magic was readable at the base address, meaning the header page was not execute-only there. If 14.00 keeps the same layout (header page readable, `.text` one page in), the first execute-only page is NOT the base — it is base + `0x1000`.

**Observations that do not resolve this:**
- All 16 bases are 4 KB aligned. The 13.60 base (`0x80000000`) is 2 MB aligned. The different alignment may reflect a different linker or load strategy, but settles neither layout.
- VP's page offset `0xB28` matches 13.60. This is a VP property, not a base property.

**To close:** A `.rodata` anchor read at a known RVA (e.g. a string constant whose file offset is known from the 13.60 binary) would distinguish the two layouts in a few reloads. This is cheap and planned as a follow-up.
