# mlfs on 14.10: the one writable filesystem, measured

Scope: `/av_contents/content_tmp` is the only path this harness can create files
in (939c). That makes Sony's filesystem implementation — `mlfs_*` symbols are
present in `docs/dumps_13.60/kernel_data.bin` — the only kernel parser that
consumes data we generate: file contents, sizes, offsets and names, with no
capability gate.

Everything below was measured on firmware 14.10 from the Lua loader.

## 947a - entry points (capture `results/phase17_new_vectors/947a_mlfs_surface_20261028_214831.txt`)

| operation | result |
|---|---|
| `open(O_RDWR\|O_CREAT\|O_TRUNC)` | fd 22 |
| `write(0x1000)` at 0 | 4096 |
| `lseek(0x3FFFFF00)` + `write(0x100)` (1 GiB sparse) | 1073741568 / 256 |
| read back at the sparse offset | 256 bytes, first dword `0xC0DE0000` as written |
| `ftruncate(0x40000000)` then `ftruncate(0x1000)` | 0 / 0 |
| `rename(a -> existing b)` | 0 |
| `unlink` twice | 0 then -1 |
| `open(255-byte name, O_CREAT)` | fd 22 |
| `mkdir` / `rmdir` | 0 / 0 |
| `getdents(0x1000)` | 4096 |

No fault, no panic. Sparse writes land, truncation up and down is accepted, a
255-byte name is created without complaint.

## 947b - inode lifetime (capture `..._20261028_214857.txt`)

| case | result |
|---|---|
| unlink while open, then write/read through the descriptor | data intact (`0x11110000` read back) |
| reopen the same name after unlink | new empty inode (`read` returns 0) — no resurrection |
| two descriptors, `ftruncate(fd2, 0)` | the first descriptor reads 0 immediately |
| `ftruncate(fd, 2^63)` | -1 |
| rename while open | descriptor keeps working, data intact, old name -1, new name opens |

That is correct POSIX inode lifetime — refcount on the open file, no stale data
after truncate, rename moves the inode.

## 948a - aio on a regular file (capture `..._20261028_215023.txt`)

Control, socketpair fd: submit `rv=0 ids=4205`, poll states `2,2`, delete
`0x80020010,0x80020010`.
File fd on `/av_contents`: submit `rv=0 ids=206`, poll states `1,1`, delete
`0x80020010,0x80020010`; repeat on the next slot, same shape.

The file descriptor changes the poll state (1 instead of 2) but the delete is
refused as in-flight in both cases, so a file backend does not open the
lock-drop window either. The 14.20 TOCTOU still has no measured trigger here.

## Position

Three bug classes a public 14.10 exploit would want — aio delete race, semaphore
object lifetime, filesystem lifetime — are each either unreachable (aio submit
never sets the in-flight word on a socketpair *or* a file) or correctly
implemented. The reachable kernel surface has now been exercised along every
argument shape we can construct from this loader; nothing has produced a
mismatched free, a stale handle or a writable kernel pointer.

## 949a - concurrency: the harness cannot overlap two syscalls (capture `results/phase17_new_vectors/949a_mlfs_lookup_race_20261028_215408.txt`)

The design was a lookup race: two children spawned with `thr_create` (child A's
first syscall `unlink(path)`, child B's `rename(path, path2)`) while the parent
looped 20,000 x `open` / `ftruncate` / `close` on the same name.

Result: both children spawned (`tids 102136`, `102137`, `rv=0`), the parent loop
ran 20,000 iterations in 0.88 s and **every single open failed**, and after the
loop both names were gone. So both children had already completed before the
parent's first `open` — again.

That repeats 912a in a second subsystem: a child created by `thr_create` runs while
the parent is inside the *spawn* syscall, and the parent's subsequent Lua-driven
syscalls all happen afterwards. The parent only yields the CPU inside a blocking
call (`nanosleep`), and it cannot issue a filesystem operation while blocked in
one. **No parent/child syscall overlap is reachable from this loader**, which is
why every race probe - aio delete, aio recreate, and now the filesystem - reports a
deterministic single winner. This is a property of the harness, not of the kernel.
