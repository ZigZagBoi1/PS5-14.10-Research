# Handler 572: Query a virtual-memory region with compatibility filtering

## Identity and scope

- Input: `handler_572.bin`, 4096 bytes, SHA-256 `341a72e9491e45854d0132355b22b3132b47488729a976eca7f7c64ce910cf24`.
- Verified exact match in `kernel_text.bin` at RVA `0x265df0`.
- First instruction: `jmp 0xabac50`; next three bytes are `int3` padding.
- Sysent metadata: 4 arguments; mapping classification `real`.
- Runtime base from supplied context: `0xffffffff8a9c0000`; all addresses below are RVAs.
- Primary analyzed body (inclusive): 0xabac50..0xabaf9c, 0xabafa0..0xabb2ed.
- The full `.asm` covers all 4,096 source bytes, plus primary implementation and selected support. Neighbor trampoline targets are not part of this syscall.

## Behavior

Queries the current process VM map near a supplied address, aligned down to a 16 KB boundary. Walks map entries and selected special-address ranges; emits a normal 0x48-byte region record, a 0x18-byte compact record, or a synthesized record for special ranges. Each visible transfer is bounded by min((uint32)user_size,record_size).

## Dispatch and subcommands

Flags bit 0 controls lookup/iteration behavior, bit 16 influences a visibility/compatibility decision, and bit 17 selects the compact record in the normal-map path. With proc+0xc81 nonzero, bits outside 0x30001 are rejected. Otherwise only bit 0 is retained. The slow special-region path emits the 0x48-byte form. No code jump table is visible in the handler.

## Permission and validation checks

Rejects unsupported flags and aligned addresses above map+0x28 with 22. An initial 0xb2bb00(4) gate can also produce 22; its exact policy is unresolved. Visibility checks use proc+0xc81, proc+0x5d4, a return-address/frame walk with a fault-tolerant fetch helper, image limits +0x5a0/+0x5a8, and several address ranges. Some no-entry/hidden results return 13 (EACCES). This operates on td->proc; there is no user-supplied PID or alternate VM-map pointer.

## Data flow and locking

address/flags -> normalization and policy -> read-lock current map -> entry lookup/traversal or process-scoped auxiliary query -> initialize/assemble local record -> unlock normal VM path -> copyout bounded prefix. A special auxiliary path performs its bounded copy while still in the map traversal, then releases auxiliary state and the map lock.

## Attack surface and limits

Review consistency across normal, compact and special-range records, initialization of every exported byte, copyout while locks are held in the slow path, and the user-frame walk termination. The normal record builder (0xaba710) and compact builder (0xabb3b0) are included as supporting code; auxiliary providers are not fully covered. An output-size cap is visible; no oversized copy or kernel-address disclosure is established solely from the query interface.

## Interpretation check

This is current-process VM introspection with compatibility filtering; the supplied dump does not establish an unrestricted kernel-memory query.
