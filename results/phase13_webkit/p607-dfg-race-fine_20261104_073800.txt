=== SECTION A: JIT Compilation Test ===

  new Function(): 83ms  (50K calls × 100-iter loop = 5M iterations)
  Regular func:   87ms  (same workload)
  eval() func:    98ms  (same workload)
  Padded func:    60ms  (5K calls, 50 padding loops each)

  VERDICT: All three function-creation methods achieve IDENTICAL

  The p606 failure was NOT caused by new Function() skipping JIT.

  Padded function (50 padding loops) runs in 12μs/call (60ms/5K).
  This is consistent with DFG-compiled code (interpreter would
  be ~100μs+ per call with 50 padding loops).

=== SECTION B: Fine-Grained DFG Race (PIVOT 60-300, step 1) ===

  PIVOTs tested: 241 (every integer from 60 to 300)
  Function: regular declaration (guaranteed DFG)
  Padding loops: 50 per call
  Deopt+recompile between each attempt

  RESULT: 0/241 hits. ZERO type confusion.

  This covers the entire plausible DFG compilation window with
  single-iteration granularity. If the race existed in DFG at
  ANY point between iteration 60 and 300, it would have hit.

=== SECTION C: Higher Range (PIVOT 500-5000, step 20) ===

  PIVOTs tested: 226 (500 to 5000, step 20)
  Same function, deopt+recompile cycle

  RESULT: 0/226 hits. ZERO type confusion.

  Ran in ~9 seconds (8.3s for 226 attempts × ~5000 iterations each).

=== SECTION D: Constant Fold Detection ===

  Test: compile cfTest(o){return o.p1[0]} with o.p1=[9.9,8.8],
        then swap o.p1=[7.7,6.6] and re-call.

  expected=7.7, got=7.7, folded=false

  VERDICT: DFG does NOT constant-fold o.p1[0].
  After swapping p1 to a new array, the function correctly returns
  the new value (7.7). This means tryGetConstantProperty is NOT
  eliminating the property load in DFG tier on PS5.

  This is the foundational mechanism of CVE-2024-23222. Without
  constant folding of property accesses, the race cannot produce
  type confusion even if the timing were perfect.

=== DEFINITIVE ANALYSIS ===

  CVE-2024-23222 is DEAD on PS5 14.10 for THREE independent reasons:

  1. FTL ABSENT: p606 Section A showed no FTL speedup. Without FTL,
     the Coruna-style race (which needs ~1ms compilation window) is
     structurally impossible.

  2. NO CONSTANT FOLDING: Section D proves DFG doesn't fold property
     accesses. Even if we hit the race window, there's no stale type
     to exploit — the DFG doesn't specialize o.p1 to a constant.

  3. 467 PIVOTS TESTED, 0 HITS: Fine-grained sweep of every iteration
     60-300 plus coarse sweep 500-5000. With deopt+recompile per
     attempt using a regular function. If ANY race window existed,
     one of 467 attempts would have hit it.

  Possible explanations:
  a. Sony's WebKit build has FTL disabled (memory/stability reasons)
  b. The DFG pipeline on 605.1.15 doesn't call tryGetConstantProperty
     for this access pattern
  c. The bug was cherry-pick patched from Safari 17.3 into this build
     (build date Sep 2026, fix was Feb 2024)
  d. The DFG's ConstantFolding doesn't remove CheckArray even when
     CFA records a concrete type (conservative behavior)
