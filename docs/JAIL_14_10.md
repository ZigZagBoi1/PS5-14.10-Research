# What a game process can actually see on 14.10

Every kernel route this repository has measured ends the same way: either the
syscall refuses the argument shape, or the process dies at the touch. The ioctl
round (`docs/DEVICE_IOCTL_14_10.md`) closed the device surface: twenty-five
`/dev/gc` commands, all of them struct fillers writing small constants.

That left one question nobody had asked. We run inside a game process, and the
console ships a sandbox around it. **What is inside that sandbox, and is there
anything in it that a kernel exploit could start from?**

This is the answer, measured on 14.10 with the Lua loader.

## Only three roots open

`probes/phase17_new_vectors/290a_fs_roots.lua` opened every plausible root:

| path | result |
|---|---|
| `/` | opens, fd 22 |
| `/app0` | opens, fd 22 |
| `/dev` | opens, fd 22 |
| `/mnt`, `/mnt/usb0`, `/mnt/usb1`, `/mnt/ext0`, `/mnt/ext1` | `-1` |
| `/data`, `/user`, `/system`, `/tmp` | `-1` |

The jail root is not the console root. It contains eight entries and none of
them is a mount point for removable media:

```
.  ..  IMt9cl0VzR  system_tmp  dev  app0  savedata0  av_contents
```

`/app0` is the game itself (`eboot.bin`, `root.pfs`, `root.pfs.000`,
`sce_discmap.plt`, `movie/`, and `sce_module/` holding `libc.prx` plus ten other
PRX files). `/savedata0` is the save data the loader lives in (`MAIN.LUA`,
`SYSCALL.LUA`, `MEMORY.LUA`, `NATIVE.LUA`, `PS5-KEXP.BIN`, `ps5-elfldr.elf`, 27
files). `/av_contents` holds `photo`, `video`, `sdr`, `extra`, `content_tmp` and
`thumbnails`. `/dev` carries 79 nodes.

## Reading a directory

The first walk printed nothing, because FreeBSD's 64-bit `struct dirent` does not
apply here. The records are 32-bit:

```
+0   d_fileno   u32
+4   d_reclen   u16
+6   d_type     u8     4 = directory, 8 = regular, 10 = symlink, 12 = socket
+7   d_namlen   u8
+8   d_name     d_namlen bytes, record padded to 4
```

Listing is `getdirentries`, syscall **196**: `getdirentries(fd, buf, nbytes,
*basep)`, called repeatedly until it returns 0. A record whose `d_reclen` does
not advance ends the buffer.

## The one live surface: `/system_tmp`

`/system_tmp` is not a temporary directory. It is the socket directory of the
system services:

```
GnmCompositor            GnmCompositorRestricted     SceImageUtilAgent
VrTracker2DomainSock     AgcCompositorSppSocket      SystemTts
redis.sock
```

A game process can `connect(2)` to some of them. `296a` opened
`socket(AF_UNIX, SOCK_STREAM, 0)` (syscall 97) against a `sockaddr_un`
(`sun_len` at +0, `sun_family` at +1, path at +2) and called `connect`
(syscall 98):

| socket | stream | datagram |
|---|---|---|
| `GnmCompositorRestricted` | **0 connected** | `-1` |
| `VrTracker2DomainSock` | **0 connected** | `-1` |
| `AgcCompositorSppSocket` | **0 connected** | `-1` |
| `GnmCompositor` | `-1` refused | `-1` |
| `SceImageUtilAgent` | `-1` refused | `-1` |
| `SystemTts` | `-1` refused | `-1` |
| `redis.sock` | `-1` refused | `-1` |

The split is the access-control boundary working: the unrestricted compositor
is for system processes, `GnmCompositorRestricted` is the door a game is
allowed to use. The three that accept are services running outside this jail,
and that is the first time this repository has reached code outside the sandbox
without a kernel bug.

## What they do with a first message

None of the three speaks first: `recvfrom` with `MSG_DONTWAIT` returns `-1` on
every connection. `297a` then sent runs of zero bytes at lengths 0, 1, 4, 8 and
64, drained after each, and reconnected to prove the service was still
accepting:

| socket | 0 | 1 | 4 | 8 | 64 |
|---|---|---|---|---|---|
| `GnmCompositorRestricted` | send 0, no answer, reconnect ok | 1 | 4 | 8 | 64 |
| `AgcCompositorSppSocket` | send 0, no answer, reconnect ok | 1 | 4 | 8 | 64 |
| `VrTracker2DomainSock` | send 0, no answer | **connect failed** | failed | failed | failed |

Two of the three accept and hold any run of zeros without answering and without
closing, which means either the connection sits in the server's queue and is
never read, or the server reads it and waits for a header we have not sent. The
probe cannot tell those apart from the client side.

`VrTracker2DomainSock` stopped accepting after its second connection and stayed
refused for the rest of the run. Either its listen backlog is one and the
service never accepts from a game process, or it entered a state after the
first client disconnected. It is a denial of service on a socket we cannot use
anyway, not a primitive, and the service was still not accepting on the next
probe.

Nothing here hands a page a chosen value. What it does establish is that the
game process holds a reachable handle into three system services, and that the
protocol each expects is the only thing between a page and their parsers. That
work needs the service binaries, which this console does not place in the jail.

## What this closes

**The USB route is dead from this process.** A USB stick mounted by the system
does not appear under `/` because this namespace has no mount point for it:
`/mnt` does not exist, and `/mnt/usb0`, `/mnt/usb1`, `/mnt/ext0` and `/mnt/ext1`
are all `-1`. The FAT driver is therefore not reachable from a game, and the
`msdosfs_readdir` padding disclosure (CVE-2020-25579) cannot be reached this
way regardless of whether 14.10 still carries it.

**No filesystem driver is reachable at all.** `savedata0` and `system_tmp` are
mounted by the system before the jail is built, and every path that would name a
raw device is outside the namespace. A game process reads files through the
kernel's VFS but never supplies a filesystem image.

**The debug graphics node is not reachable.** `298a` tried every node the
earlier rounds could not open or never reached. `dbggc`, `sbl_srv`, `encdec`,
`uvd_dec` and `mp3` refuse both `O_RDONLY` and `O_RDWR`, so the debug variant of
the graphics driver - the one that would plausibly expose commands the retail
node does not - is closed to a game process by the same credential check that
closes the update devices. `sce_zlib`, `ajm`, `ajmi` and `rng` open read-only,
and `camera` opens both ways.

`299a` then swept the four read-only nodes across every command byte, direction
and length: each answers exactly one command, `0x4004667A` (`FIODTYPE`), which
is the file layer's, not a driver's. `camera` is the remaining node with a
driver table, and its twenty commands (`0x40040000`-`0x40040013`) were still
unmeasured when this write-up went out - `300a` is written and queued behind a
busy loader.
