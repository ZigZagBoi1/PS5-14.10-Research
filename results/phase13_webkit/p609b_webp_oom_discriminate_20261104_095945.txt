--- Discrimination Verdict: OOM CONFIRMED ---

1. HEADER PARSING IS SAFE: 16384x16384 Image loads without crash when drawImage
   is not called (T6: NOCANVAS-OK). The VP8L header parser correctly reads
   dimensions from minimal compressed data without triggering any buffer overread.

2. CRASH IS IN PIXEL BUFFER ALLOCATION: The crash occurs during drawImage, which
   triggers actual pixel decode. The decoder must allocate W×H×4 bytes for the
   output pixel buffer. At 12288x12288 (576MB) and above, this allocation fails.

3. CLIP DOES NOT HELP: drawImage with a 64x64 clip region on a 16384x16384 image
   still crashes (T7). WebKit allocates the FULL pixel buffer even for partial draws.
   At 8192x8192 (256MB), clip works fine (T8).

4. NO HEAP RESIDUE: T9 sprayed 1000×256B buffers with 0xBB bytes, then decoded a
   64x64 VP8L from 4B of compressed data. All 4096 pixels were zero. The decoder
   does NOT read past its compressed data buffer into heap memory. The error recovery
   path cleanly zeros the output.

--- WebP Attack Surface: CLOSED ---
Combined with p609 (21 generic fuzzing tests):
- VP8L and VP8 both functional on PS5 14.10
- Decoder is robust: garbage → zeros, truncation → ERR, oversized → OOM
- Zero heap residue in any pixel data under any condition
- CVE-2023-4863 specific Huffman trigger untested but generic surface is dead
- NOT useful as a read primitive for WebProcess text base discovery
- NOT useful as a write primitive (no overread/overwrite observed)
