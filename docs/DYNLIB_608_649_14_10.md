# dynlib 608 / 649 / 597 on 14.10: the record is sanitised, the oracle is live, 597 still dies

Measured 2026-11-04 21:01-21:02 (probes 1198a, 1199a). Loader responsive both times;
1199a ended with the loader dead and needed a relaunch.

Captures: `results/phase17_new_vectors/1198a_dynlib_get_info_ex_records_20261104_210133.txt`
(41010 bytes, COMPLETE, loader alive) and
`results/phase17_new_vectors/1199a_priv_grant_597_20261104_210201.txt` (1358 bytes, no
`=== DONE`, process death).

## 1. 608 `dynlib_get_info_ex` hands out no kernel addresses

ABI confirmed by measurement: `a0` = module id (u32), `a1` = flags, `a2` = pointer whose first
qword must be `0x1a8`, `a3/a4` unused. `rv = 0` for ids `0x00`, `0x13`, `0x14` and for **all four
flag values 0..3** - the flags argument changes nothing measurable, the record is identical.

For id `0x13` (`libSceFios2.prx`), record base = `B`:

| offset | value | note |
|---|---|---|
| +0x000 | `0000000000000000` | size field comes from the caller, stays 0 |
| +0x008 | `5362696C 69466563 2E32736F 00787270` | `libSceFios2.prx` inline, NUL at +0x016 |
| +0x108 | `00000013 00000000` | id, then zero |
| +0x110 | `00000001BCC40020` | userland VA |
| +0x128 | `00000001BCBDC000` | userland VA |
| +0x130 | `00000001BCC22D60` | userland VA |
| +0x148 | `00000001BCC36E24` | userland VA |
| +0x150 | `00000001BCC2F890` | userland VA |
| +0x158 | `00007594000016C4` | two dwords |
| +0x160 | `00000001BCBDC000` `0006000000000001` | segment base + (flag, size 0x60000) |
| +0x170 | `00000001BCC40000` `0012C00000000001` | second segment, size 0x12C000 |

**A kernel-qword scan (`hi >= 0xFFFF8000`) over the whole 0x1a8 record found nothing, for every id
and every flag value.** The 608 converter translates each module field into a userland VA; the raw
`[r15+0x78] / [r15+0xe8] / [r15+0xf8] / [r15+0x108]` values that the static listing reads are
*already* userland VAs relative to the module base. So 608 is not a read primitive - but it is a
free, bounded, unprivileged view of the module table, which nothing before this had.

Also measured: id `0x00` is `boot.bin` with VAs around `0x6BEE8000`-`0x6C361EA8` (the low,
statically loaded image) and id `0x14` is `libc.prx` around `0xF5F74000`-`0xF608C020`.

## 2. 649 `dynlib_get_obj_member` agrees with the record, field for field

`a0` = id, `a1` = member index 1..8, `a2` = 8-byte out pointer. Measured on id `0x13`:

| idx | rv | out | equals 608 record field |
|---|---|---|---|
| 1 | 0 | `00000001BCBDC000` | +0x128 |
| 2 | 0 | `00000001BCC22D60` | +0x130 |
| 3 | 0 | `00000001BCC36E24` | +0x148 |
| 4 | 0 | `00000001BCC2F890` | +0x150 |
| 5 | -1 | not written | unset arm on 14.10 |
| 6 | -1 | not written | unset arm on 14.10 |
| 7 | 0 | `00000001BCC40020` | +0x110 |
| 8 | 0 | `00000001BCC40000` | +0x170 (second segment base) |

Two independent converters returning the same eight values is a clean cross-check of both: the
record layout in section 1 is not a probe artefact. Indices 5 and 6 are the two arms Sony left
empty in this build - the 13.60 jump table has eight entries, so on 14.10 two of the six struct
offsets either moved or return an error deliberately.

## 3. The privilege-mask oracle works; 597 still kills

`1199a` P0 read 608 for ids `0x13`, `0x00`, `0x14`: all three returned `rv = 0` with the segment
fields **filled, not zeroed**. Level 2 of the mask is therefore **clear** for a plain game process,
exactly as the static reading predicted (`0x8b4ebb00` returns 1 when `[ctx+0x140] & 2` is set, and
608 zeroes `rec+0x128/0x130/0x1a0` in that case). The oracle is usable.

Then `1199a` printed `[597] --- shape 1 about to run ---` and the process died in 6.891 s with no
`=== DONE`. Shape 1 was the **six-zero** shape, which the presence sweep had already recorded as
lethal. The probe's own ordering wasted the connection: shapes 2 (`arg1 = 0x13`) and 3
(`arg1 = 0x13, arg2 = 0x1a8, arg3 = buffer`) never ran.

So after two measurements, the state of the question is:

* 597 is lethal with six zero arguments (reproduced twice, on two different builds of the loader).
* It has **never** been called on 14.10 with an argument that could plausibly survive.
* Its 13.60 body never reads `uap`, so the death cannot be the documented grant path itself; the
  candidates are gate A's predicate calls, a genuinely different 14.10 body, or an absent slot
  (an absent slot also terminates the caller - `docs/SYSCALL_ABSENT_VS_LETHAL.md`). The presence
  map's own preamble says a "kills" row means *not callable with zeros*, not *absent*.

`1199b` (`probes/phase17_new_vectors/1199b_597_arg_shapes.lua`) inverts the order: neighbour
control 596, then the 608 oracle, then `arg1 = mapped buffer holding module id 0x13`, then the
`0x1a8`-record convention with `arg2 = 0x40`, and only then the lethal zeros - each surviving
shape followed immediately by the oracle diff. One relaunch now buys a real answer either way:

* 597 returns with a mapped pointer and the oracle flips -> the mask has an unprivileged writer and
  bit `0x40` becomes the next thing to spend on a syscall that tests it.
* 597 dies with a mapped pointer too -> the slot is not callable on this firmware at all, the grant
  route closes, and the mask's only other writer is the `0x3210eb` cluster
  (`or dword [rax+0x140], 0x10000` / `and ..., 0xffffefff`), which still needs its owning
  function resolved.

## 4. Probe-authoring lesson

Order arguments by lethality, not by curiosity. Both 1199a and the earlier 1193b lost their whole
connection to a shape listed first for readability. Put the expected-lethal call last, print a
banner before every line that can kill, and never let the one shape you care about share a
connection with a shape you already know dies.

## 5. 1199b: 597 dies with a mapped pointer too (measured 21:07)

```
[596] control rv=0                       <- neighbour fine, syscall path fine
[608] P0 id=13 +128=0000000173738000 ... <- oracle baseline, level 2 clear
[597] --- S1 arg1=mapped{B}=0x13, args2..6=0 ---
(no further output, 8.828 s, no === DONE)
```

`arg1` was a mapped `0x400`-byte buffer whose first dword is `0x13`; `args2..6` were zero. The process
died anyway. So the zero-argument kill was not about the arguments being zero.

Combined with the static reading - **597's body never touches `uap`** - the three remaining
explanations are:

1. **The slot is not callable on 14.10.** An absent or deliberately poisoned slot terminates the
   caller (`docs/SYSCALL_ABSENT_VS_LETHAL.md`); this is indistinguishable from a faulting handler
   from userland, and both look exactly like what we measured.
2. **The 14.10 body differs** and dereferences something we are not providing.
3. **Gate A (`0x8b48ce10`) faults** in a 14.10-only path. In 13.60 it is three predicate calls and a
   global read; nothing in it can fault on our account.

Nothing further is spent on 597 this session. Even a successful grant would buy bit `0x40`, and a
whole-image disassembly finds **zero readers** of that bit: `0x8b4ebb00` is called with levels
`0x10, 1, 2, 2, 8, 4, 4` and nothing else. 597 is a genuine unprivileged capability grant in the
13.60 image, but on 14.10 it is unreachable, and its payoff was never kernel memory - it is a
dynlib-capability bug, not a read/write primitive. Parked, with the measurement recorded.

### What the mask's other writers turned out to be

Whole-image disassembly of every `[reg+0x140]` immediate writer, with each site walked back to its
enclosing function, gives 20 sites in 15 functions. Only `0x34c88d` (597) touches the loader
context. The three that looked most promising - `0x3210eb` `and [rax+0x140], 0xffffefff`,
`0x321352` `and [rax+0x140], 0xfffff7ff`, `0x321d14` `or [rax+0x140], 0x10000` - all operate on
`[r14+0x28]` inside functions that take locks with `lea rdi,[rip+...]` and do socket-buffer
arithmetic (`imul` against a global limit, `cmp ecx, edx`): a different `+0x140` field on a
different object, not the capability word.
