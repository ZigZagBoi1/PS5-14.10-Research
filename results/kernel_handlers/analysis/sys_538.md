## Behavior and data flow

At `0xbafa80`, validates attributes, copies a user name with bound `0x20`, allocates a `0x58`-byte object and initializes its 64-bit pattern from argument +0x10. Initializes a lock, wait channel and an empty waiter list. It reserves a handle in the calling process’s namespace (`process + 0xc48`). Attribute bit `0x100` additionally registers the object by name/type `0x110` in a shared registry; otherwise shared-reference state is zero. Stores the creating PID at object +0x54. Successful publication writes the handle to `td + 0x408`, and returns status 0. Handle reservation failure returns `0x23`; name-copy and shared-registration errors unwind the reserved handle and allocations. An optional logging path does not control the operation’s success.

## Dispatch and subcommands

No selector-driven jump table or user-chosen function pointer in the entry. This is one operation in the shared type-0x110 family: create 538, delete 539, open 540, close 541, wait 542, poll 543, signal 544, clear/AND 545 and cancel/reset 546. These operation names are analyst inferences from the code, not recovered symbols.

Attributes outside mask `0x133` are rejected. Low bits 0/1/2 are allowed, with zero normalized to 1 and 3 rejected. Bits 0x10/0x20 are mutually exclusive; neither is normalized to 0x10. Bit 0x100 selects shared-name registration.

The recovered wait helper establishes the object attribute semantics: low value 1 appends waiters in FIFO order, while low value 2 inserts by a thread-priority field. Attribute 0x10 rejects an additional waiter when waiter_count is nonzero; the mutually exclusive 0x20 is the multiple-waiter alternative.

## Permission checks and validation

No direct credential gate appears before allocation/publication. Non-null name, bounded string copy, attribute mask and mutually exclusive fields are checked. Handles are allocated in the caller’s process namespace; shared naming/collision/access behavior is delegated to `0x994870` and related registry code.

## Attack surface and limits of conclusions

Name ingestion, registry collisions, handle-exhaustion rollback and shared-object reference lifetime are the main boundaries. The object allocation is fixed-size, and name copying is bounded. The global registry’s policy must be examined before claiming cross-process access. Review creation/open/delete/close races across shared references; the wrapper alone does not establish a race or use-after-free.

This is static analysis of a recorded kernel image. A missing check in this body does not establish that the syscall entry path, object namespace, or external callees impose no checks. Review points are not confirmed vulnerabilities or exploit primitives. No target code was executed.
