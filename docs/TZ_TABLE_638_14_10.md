# Syscall 638 is `utc_to_localtime`, and its "kernel pointer" is a 1968 epoch key

## The claim this refutes

Probe 1027a recorded that `638(input, 0, buf, 0x100)` writes a deterministic
16-byte pair into `buf`:

    FFFFFFFFFDC7BB70 E10

which reads as "a supervisor-range address plus a length of 0xE10 = 3600", and
1029a then showed, through the #PF presence oracle, that `0xFFFFFFFFFDC7BB70`
is mapped. The open question was whether this is a KASLR leak (a relocated
kernel pointer), a per-boot allocation, or something else.

It is neither. `0xFFFFFFFFFDC7BB70` is the **int64 key of the first record of a
timezone transition table**, in two's complement: `-37242000` seconds, i.e.
`1968-10-26T23:00:00Z`. `0xE10` is the record's `offset` field, 3600 seconds —
one hour. 1029a's "mapped" answer was equally uninformative: the address was
chosen by 1027a's own arithmetic, not by the kernel, and 1.6 GB above the image
base the kernel half is mapped no matter what.

## What the syscall actually is

`docs/sysent-names-13.60.csv` names 638 `utc_to_localtime` and 639
`localtime_to_utc`. The recovered 13.60 body
(`results/kernel_handlers/decompiled/sys_638.c`, RVA `0x6be5c0`) agrees
exactly, and both are single functions with no permission check:

| element | 13.60 RVA | 13.60 VA |
|---|---|---|
| record table (258 × 16 B used of 512 slots) | `0x42d5920` | `0xffffffff8e2d5920` |
| record count (`int32`) | `0x42d7920` | `0xffffffff8e2d7920` |
| mode (`int32`) | `0x47105b0` | `0xffffffff8e4305b0` |
| table lock | `0x42d5900` | `0xffffffff8e2d5900` |
| copy-out helper | `0x0c191d0` | `0xffffffff8ac191d0` |

The count global sits exactly `table + 0x2000` = 512 records after the base, so
the table region is 512 slots wide by construction.

### ABI (measured, then matched to the body)

    struct { int64_t input; uintptr_t value_out, record_out; uintptr_t correction_out; }

* `uap+0x00` — input, signed epoch seconds.
* `uap+0x08` — 8-byte out: `input + offset + correction` of the selected record.
* `uap+0x10` — 16-byte out: `struct { int64_t key; int32_t offset; int32_t correction; }`.
* `uap+0x18` — 4-byte out: the nearest non-zero `correction` found by scanning
  backwards from the selected index.

Each destination is skipped when its pointer is zero; the first failing
`copyout` returns its errno **after** the earlier copies have already landed.
That is why 1027a saw data plus `rv = -1`: its fourth argument was the literal
`0x100`, an unmapped user address, so the 4-byte copy returned `EFAULT`.
With all three destinations valid, every call in 1160a/1161a returned `rv = 0`.

### Selection rule (why stepping input by 1 does not advance)

`index = (upper_bound of key <= input) - 1`, bounded by `[0, count-1]`. Probing
`input = key+1` therefore lands on the *same* record until the next key. 1161a
walks the table by exponential search plus bisection between record boundaries.

## The table, measured (1161a, 258 records, 12 380 calls)

* Records: **258**, keys strictly ascending, spanning `-37242000`
  (1968-10-26T23:00Z) to `4096163600`-ish (late 2099). Every key falls inside
  the 1900..2100 window; `[C]` found 0 out-of-range records.
* `offset` is **0 in every record**; `correction` alternates **0 / 3600** at
  half-year boundaries (keys 182.6 days apart), and `nearest` is 3600 throughout
  the observed range — a daylight-saving transition table, one hour on, one hour
  off, for a single zone.
* 258 < 512, so the handler never leaves its own window: `index` cannot exceed
  `count-1` and `count` is not attacker-influenced. `[T]` reports
  `records_gt_512 = false`.
* Arithmetic check: 1160a's second call used `input = key+1 = -37241999` and got
  `value = -37238399 = input + 3600`; 1161a's row 1 shows
  `value = 0xC000000000000000 + 0xE10` — the same `input + offset + correction`
  with the caller's own (absurd) input. The `[A]` line in both captures compares
  against `key`, not against `input`, so its printed "delta" is a probe
  artefact and not a finding.

## What this gives us

The first **confirmed kernel read on 14.10 that returns real kernel bytes** — not
a presence oracle, not an arithmetic constant:

    userland <- *(uint8_t*)(0xffffffff8e2d5920 + 0x10*i)  for 16 bytes, i in [0, 257]

reachable as uid 1, with no credential in the path, 16 bytes per call, and an
index selected by the caller's input. It is bounded to a table whose contents are
public timezone data, so it is not useful in itself. It matters for three
reasons:

1. It is an existence proof that the **unguarded `copy_out` pattern**
   (`0xffffffff8ac191d0` called with a kernel source, no `priv_check`, no
   `copyout` size check against a caller length) is live on 14.10 — the corpus
   had only ever audited it for *writes* and for reversed arguments.
2. It fixes the shape to look for elsewhere: a **global table + global count +
   scaled index + copy_out**. Any sibling whose `count` exceeds its table, whose
   stride differs from the copy length, or whose bound is `<=` instead of `<`
   turns the same helper into an out-of-bounds `.data` read.
3. It removes `0xFFFFFFFFFDC7BB70` from the "possible kernel pointer" list, so
   the corpus claim "no syscall hands userland a kernel pointer" survives intact
   and no longer has this exception hanging off it.

## What it does not give

No out-of-bounds index, no attacker-controlled destination, no write, and no
pointer: the 16 bytes always come from the same 258-record window, and `offset`
is 0 for every record. 639 (the inverse) uses the same table with the same
`[0, n-1]` bound and two extra interior reads (`table[lo-2]`, guarded by
`lo >= 2`), so it adds nothing.

## The audit this opened, and its result (same day)

The 62-handler number in the first draft of this note did **not reproduce**: that
count came from a substring grep over the asm corpus that matched comment lines
mentioning the helper's RVA. Measured properly
(`docs/COPYOUT_TABLE_INDEX_AUDIT.md`):

| item | count |
|---|---|
| asm files with a byte-level `call ffffffff8ac191d0` | **19** |
| byte-level call sites | 59 occurrences, 42 distinct sites |
| decompiled files naming the helper | 27 |
| functions with a global table + scaled index reaching the copy | 2 — the 638 and 639 bodies, i.e. this one table |
| provable out-of-bounds table reads reaching userland | **0** |

Every other copy source is a stack frame or a caller-supplied array. The
"index from table contents, loop bound from another table's count" sub-pattern
does exist, but in the shared body of 618/620/624/628/637/642 the index is written
into the *caller's* array, not into kernel memory, so it is not an OOB read.

The one structural observation worth carrying forward: the table is bounded by
*geometry*, not by a check. The count global sits exactly `512 * 0x10 = 0x2000`
bytes after the table base, and the only writer of the count (636) accepts
`1..512`, so "table window 0x2000" and "count <= 512" are the same fact and
cannot drift apart.

If a future firmware writes the 638 search exit as `jbe` instead of `jb`,
`table[count]` would be the count global itself and 4 bytes of `.data` would leak
to userland — that is the only reachable OOB shape this table admits.

All three copy-out shapes are now closed in [the class summary](COPYOUT_CLASS_CLOSED.md); this
table remains the only in-class shape the corpus contains.

## The write half: 636 `set_timezone_info` is the same table, behind bit 62 (1162a)

The 636 body (`results/kernel_handlers/decompiled/sys_636.c`, target
`0xffffffff8b07e4d0`) is the inverse of 638 and it is a genuine bounded kernel
write — 8 KB of user data into the same `.data` table:

    if (!sub_ffffffff8afc8f90(PTR(td,0x140))) return 1;        // bit 62 of cred+0x60
    if ((uint32_t)(a->count-513U) < 0xfffffe00U) return 22;    // accepts 1..512
    sub_ffffffff8ac19280(a->records, 0xffffffff8e2d5920, count*16);  // copyin
    *(uint32_t*)0xffffffff8e2d7920 = a->count;
    sub_ffffffff8b35e490(0xffffffff8e2d5920, a->count, 16, 0xffffffff8ac2ba00);

1162a probed the ordering of the two checks with seven argument shapes on 14.10:

| call | result |
|---|---|
| `636(NULL, 1)` | `-1`, `errno = 1 EPERM` |
| `636(buf, 0)` | `-1`, `errno = 1 EPERM` |
| `636(buf, 1)`, `(buf, 2)`, `(buf, 512)` | `-1`, `errno = 1 EPERM` |
| `636(buf, 513)`, `(buf, 65536)` | `-1`, `errno = 1 EPERM` |

Every shape returns `EPERM` and none returns `EINVAL`, so **the credential test
runs before argument validation** and no argument games reach the copyin. With
bit 62 the same call would overwrite up to 512 records of the timezone table and
set its count — a reliable 8 KB write at a fixed RVA, which is what the
capability is worth to whoever holds that bit.

## The 639 measurement: prepared, reviewed, and now run (1163a, 2026-11-04 14:52)

1162a died at `637(0,17)` before it reached 639, so 639 has never been called on 14.10. It is now a
probe of its own: `probes/phase17_new_vectors/1163a_639_five_slots.lua` (254 lines, `CRASH_CLASS:
SAFE`), reviewed by a correctness reviewer and a console-safety reviewer and fixed by both.

**ABI, read from the body (STATIC).** `sys_638.c:388` takes the policy as `(int)param_2[1]` and
`:444-460` copies 8, 16 and 4 bytes from `param_2[2]`, `param_2[3]`, `param_2[4]` — i.e. five 8-byte
slots:

    +0x00 int64  input        +0x10 uintptr value_out (8 B)
    +0x08 int32  policy       +0x18 uintptr record_out (16 B)
    +0x08 int32  pad          +0x20 uintptr correction_out (4 B, "nearest")

The loader's `fcall` binds six registers (`.local/loader_payload/native.lua:34-41`), so a fifth
argument is delivered; the uap is the kernel's own register-copied array, so no pointer in it can be
forged, and `sys_639.asm` contains no `copyin` at all — three copy-outs and nothing else.

**Arithmetic, and a branch worth knowing.** `:443` computes `value = input - offset - correction`.
But `:436` tests `_DAT_8e4305b0 < 0` first and, in that branch, sets the correction term to 0 and
masks the offset to 32 bits: `value = input - offset`. The probe's `[B]` row prints `delta`, so the
two cases separate without a new argument: `delta == 0` is the normal path, `delta == correction`
is the mode branch.

**The guard, and the one call that can panic.** 639 reads `table[lo-2]`, one record further back
than 638 ever reaches, under `:389` `if ((int)lo < 2 || policy < 0)` — so `lo-2 >= 0` and the
address stays inside `.data`. `:431` re-checks `idx < count`. If 14.10 had dropped that guard the
index `-1` is **zero-extended** (`:3424 lea -0x2(%rcx),%r9d` / `:3427 mov %r9,%r11` / `:3428 shl
$0x4`), giving `0x0000000F8E2D5918` — a user-range page — and the load at `:3430 movslq
0x8(%r11,%rdi,1)` is a plain `mov` with no `pcb_onfault` behind it: a kernel `#PF` there **panics**,
it does not return `EFAULT`. That single call (`[F2]`, input `0xFFFFFFFFFF000000`, below the first
key) is therefore the last row of the probe: everything else is already on the wire when it runs, so
a capture that stops at `[F2]` is itself the answer "guard absent on 14.10".

**What the probe settles — measured.** Capture
`results/phase17_new_vectors/1163a_639_five_slots_20261104_145220.txt`, status COMPLETE, 0.032 s,
process alive at the end (`pid=80`), no panic:

| row | measurement |
|---|---|
| `[A]` | five slots accepted, `rv = 0` with all three destinations valid, key `-37242000`, off `3600` |
| `[B]` | `value = input - offset - correction` with `delta = 0` on all three inputs — the `_DAT_8e4305b0 < 0` branch is **not** taken on 14.10 |
| `[C]` | zero destination skipped, the other two written, `rv = 0` in all four shapes |
| `[D]` | wild address in the **last** slot: `-1`, `errno = 14 EFAULT`, while value and record have already landed |
| `[F]` | input `0x100000000` returns key **`4128627600`** — past 2100-01-01 and past 1161a's horizon |
| `[F2]` | input below the first key returns record 0 with `rv = 0`: **the `lo < 2` guard runs**, so the panic path above does not exist on 14.10 |
| `[G]` | 638 on the same input returns value `3600` (it adds where 639 subtracts) |

So 639 is a second bounded read of the same table, reachable as uid 1, with one extra in-table
record per call and one more copy-out (`nearest`) — and the panic hypothesis is refuted by
measurement rather than by reading the 13.60 body.

**Two open ends this leaves.** First, `[E]`'s policy sweep is *vacuous*: every case used input 0,
which gives `lo = 1` and takes the `lo < 2` branch before the policy is read, so policy was never
exercised. Second, the table demonstrably continues past 1161a's `past-2100` stop — key
`4128627600` exists, so the 258-record figure is a horizon-limited dump, not the table's size. Both
are measured by `probes/phase17_new_vectors/1164a_638_tail_and_policy.lua`.

## 1164a: the tail is two more records, and the policy slot is a no-op (2026-11-04 15:01)

Capture `results/phase17_new_vectors/1164a_638_tail_and_policy_20261104_150148.txt`, COMPLETE,
0.047 s, `pid=80` alive at the end, no panic. Both reviewers passed the probe (correctness
`80cde01b`, console safety `690cc146`); the correctness pass caught one blocking bug before the run
— see below.

| row | measurement |
|---|---|
| `[C]` | 638 and 639 select the **same record** for input 1000000000: key `985482000`, off 0, corr `3600`, nearest `3600` |
| `[A]` | the walk steps 90 days at a time and stops on "three probes with an unchanged key and an input more than four years past it": 3 distinct keys, **highest = `4128627600`**, `stop=stable+4y` |
| `[AV]` | the top is confirmed by a second route: 639 from `4528627600` (13 years past it) clamps to **the same key**, and 638 at `key-1` lands strictly lower (`4109878800`) |
| `[A2]` | walking backwards from the top: `4109878800`, then `4096573200` — **exactly 2 records above 1161a's horizon**, so the table holds **260 records** (indices 0..259) |
| `[B]`/`[B2]` | policy 0 / 1 / 2 / `0xFFFFFFFF` all give an identical key, offset, correction and *nearest*, at two different indexes (`lo ~ 60` and another): `selection_same_for_all_policies=true`, `delta=0` |

**Consequences.**

1. **The table is 260 records, 4160 bytes (`0x1040`) of a 512-slot, 8 KB window.** 1161a's 258 was
   indeed a horizon artefact, but only two records were hiding: keys `4109878800`
   (≈ 2100-03-27) and `4128627600` (≈ 2100-11-04). The count global at `table+0x2000` therefore
   reads 260 on this image, and the "512 slots but only N records" mismatch is an image property,
   not an attacker-controlled one: 638/639 bound the index with that count, so the reachable read
   window is `[table, table+0x1040)` and nothing in it is outside the table.
2. **The policy slot is inert on 14.10.** 639's `policy` (`(int)param_2[1]`) gates only the
   `lo-2` lookback under `:389`, and neither the selected record nor the 4-byte `nearest` output
   moved for any value tried, including `0xFFFFFFFF` (which is negative as `int` and should have
   taken the `policy < 0` half of the guard). So the lookback does not feed any copy-out field on
   this firmware: 639 is 638 with a subtraction and an extra destination, not a second table walk.
3. **The `nearest` output is not the record's correction.** `[B2]` returned `corr = 0` with
   `near = 3600` — so `correction_out` is computed from something else (likely the correction of
   the nearest *record*, or the image's global mode at RVA `0x47105b0`), not from
   `record.correction`. Nothing follows from it for us; recorded so the next reader does not
   mistake it for a record field.

### The blocker the review caught, worth remembering

The first version rebuilt the key by sign-extending the two dwords **independently**, so every key
at or above `2^31` printed negative (`4096573200` → `-198394096`). Both walks in this probe live
above `2^31`. The consequence was not a cosmetic print: `[A]`'s stop test (`input > key + 125e6`)
was satisfied by the bug, so it quit three probes past the horizon, and `[A2]`'s guard
(`key > 4096573200`) was false, so the backwards walk never ran and reported **0 records above the
horizon** — the exact opposite of the truth, printed with total confidence. Fixed to one `key64`
helper, `si32(high) * 2^32 + u32(low)`, with a sentinel check so an untouched record buffer never
prints the `0xA5A5A5A5` fill as a 2058 key. Lesson: on this table every key above 2038 is
"negative" to a naive dword reader, and a walk whose stop condition depends on a key it computes
with the same bug will confirm the bug.



**Status:** measured on 14.10 (probes 1160a, 1161a, 2026-11-04). Closes the last
in-band "kernel pointer handed to userland" candidate in the 14.10 corpus.
