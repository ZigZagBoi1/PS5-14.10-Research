=== WHY THIS MATTERS ===

v919 graded the FontFaceSet write-after-free "behaviorally inert" because
the only observable was the status byte (+0x82 = Success readback). This
run shows the corruption IS visible in a SECOND channel: the carrier's
style property (constructed "italic") degraded to "normal" after the
free+engine-write cycle. The control leg proves the degradation is
caused by the free+write cycle, not by the construction or the channel.

The specific mechanism: zero-at-free (v909, byte-grade) scrubbed the
carrier's style property storage during the free+reclaim cycle, and the
engine's post-free setStatus at +0x82 wrote its value into the scrubbed
region. The style readback was degraded BEFORE our census ran — the
control leg never went through the free cycle, so its italic survived.

This is an impl-scale scrub witness obtained ZERO addresses: the getter
reads its own backing, no forged pointer, no Gigacage dependency. Per
the cobrajet pre-registration, branch (b) is publishable.

=== INTERESTING SECONDARY: status VALUE = "error" ===

p640 (the 14.10-era measurement) showed the engine writing Success(3) at
+0x82 and the JS-visible status flipping to "loaded". This run shows
"error" on 14.22. The value DIFFERS — which is exactly what the board
pre-registration asked for ("the value is what separates a foreign write
from a lifecycle race"). Two readings:
  (i)  the +0x82 offset is a 14.10-era offset; on 14.22 the layout
       shifted and the setStatus write landed on a DIFFERENT field —
       the style descriptor storage or a neighbour — causing a
       cascading corruption that surfaces as "error" in status AND
       "normal" in style. If true, this is a partial-overwrite signal
       on a 14.22-specific layout.
  (ii) the carrier's own load lifecycle raced: the local() source
       failed and set Error through the NORMAL path (the engine's
       FontFace::load continuation runs even without an explicit
       .load() call if the promise resolution chain touches the
       status). If true, the "error" is lifecycle noise, and the
       style corruption (italic → normal) is still the real signal.
The pre-registration only required the VALUE to be beaconed; both
readings are publishable.

=== THE WIDER TWIN QUESTION ===

The twin (idx=win+1) reads "normal" too. This contradicts a
single-chunk corruption model: the setStatus write should only touch the
chunk that was reclaimed (carrier 0's chunk = the freed target chunk).
If carrier 1's style ALSO degraded, the corruption is wider than one
chunk — either the zero-at-free scrubbed the whole arena region around
the freed slot, or the font style rebuild (inside the getter) touched
all freshly-constructed faces. This is a measurable angle for the next
probe: construct carriers with DISTINGUISHABLE style values (some
italic, some oblique) and map exactly which ones degrade.

=== THE NEXT PROBE (v931, design) ===

Per-carrier style map: 160 carriers with ALTERNATING style descriptors
({style:'italic'}, {style:'oblique'}, {style:'normal'}) — after the
free+write cycle, beacon each carrier's style readback in a single
line. The degradation MAP tells us:
  - whether the corruption is confined to the reclaim target's
    neighbourhood or is arena-wide
  - whether the corruption respects the descriptor VALUE (all become
    "normal") or the VALUES per-offset (some become "error"-shaped
    garbage)
  - whether the pre-free state was attacker-controlled (attacker-
    supplied style → attacker-known pre-image → post-image diff = a
    bitmap of what the engine wrote where)
This map is the bridge between "the write is visible" and "the write is
directable" — which is the path from the FontFaceSet UAF to a partial
overwrite on 14.22's actual layout, the blocker since v916.
