# 379 mtypeprotect and 547 query_memory_protection: what the bytes actually say

Static, 13.60 dump (`docs/dumps_13.60/kernel_text.bin`, base 0xffffffff8a9c0000, offset == RVA).
Written after `docs/CREATIVE_ROUTES_II_14_10.md` proposed both as routes; the two claims checked
here correct that document in two places. Neither syscall has been executed on the console yet.

## 1. Syscall 379 — mtypeprotect, body RVA 0xabbd80, narg 4

```
abbd8e  mov rbx,[rsi]        ; uap[0x00] = va
abbd91  mov rcx,[rsi+8]      ; uap[0x08] = len
abbd9a  add rcx,rbx          ; end = va + len
abbd9d  jb  0x8b47be44       ; carry  -> EINVAL 22
abbda3  lea r14,[rcx+0x3fff]
abbdaa  and r14,~0x3fff      ; page-align the end upward
abbdb1  cmp r14,rcx
abbdb4  jb  0x8b47be44       ; second wrap check -> EINVAL
abbdba  mov r15d,[rsi+0x10]  ; uap[0x10] = id
abbdc8  mov edi,r15d
abbdcb  call 0x8ad833e0      ; gate(id, td_proc)
abbdd0  test eax,eax
abbdd2  je  0x8b47bdf5       ; zero -> EINVAL 22
abbdd8  mov edx,[r12+0x18]   ; uap[0x18] = prot
abbde2  cmp byte [rcx+0xc81],0
abbde9  je  0x8b47bdfc       ; c81 == 0 -> LOOSE table
abbdeb  test edx,0xfc08      ; c81 != 0 -> STRICT table, reject 0xfc08
abbdfc  test dl,8            ; LOOSE table rejects only bit 3 (0x08)
abbe01  mov eax,edx
abbe14  shr eax,1
abbe19  and eax,0x141        ; bits 0,6,8 duplicated from bits 1,7,9
abbe1e  or  eax,edx          ; protbits = ((prot>>1)&0x141)|prot
abbe27  call 0x8ac8d3c0      ; vm_map_protect(vmspace, va&~0x3fff, end, id, protbits)
abbe3a  lea rdx,[rip+0xe20173]
abbe41  mov eax,[rdx+rax*4]  ; return code 0..9 mapped through a table to an errno
```

Confirmed: **there is no comparison of `va` against `vmspace+0x28`.** Syscall 547 and 572 both
have that bound; 379 does not. Whether an out-of-range `va` then survives vm_map_protect is the
open question, and it is a single console call away.

## 2. Correction: 379 cannot read proc+0xc81

`docs/CREATIVE_ROUTES_II_14_10.md` §R5/R1 claims that `379(va,len,id,0x4000)` returns EINVAL when
`c81 == 1` and succeeds when `c81 == 0`, making the byte user-readable. That is not what the
bytes do. 0x4000 sets **no** bit of the strict mask 0xfc08 and **not** bit 3 of the loose test, so
both tables accept it, and the two paths are indistinguishable from userland. The same holds for
every prot the map itself accepts (1, 2, 4): both tables accept those too. There is no prot value
that one table rejects and the other accepts *and* that vm_map_protect would accept, so **the c81
selector is not observable through 379's return code.** It is observable through 547 (below).

## 3. Where c81 is written

Whole-image scan for writes to `[reg+0xc81]` across the text segment gives one site, RVA
0x38f7bf:

```
38f780  movzx r9d,byte [r15+8]
38f785  cmp r9d,2
38f789  jae 0x8ad4f7a0
38f78b  xor ecx,ecx          ; cl = 0
38f78d  cmp r12d,1
38f791  jne 0x8ad4f877
...
38f7b7  mov cl,1             ; cl = 1
38f7b9  mov rax,[rbx]
38f7bc  mov rdi,rbx
38f7bf  mov byte [rax+0xc81],cl
38f7c5  call 0x8ad50520
```

`rbx` is a process being brought up and `r12d` is a launch-parameter selector (1 or 2), not a
syscall argument. The byte is set once at process creation. No syscall in the image writes it, so
a running process cannot flip its own policy byte; the only way to run under the strict table is
to be started with the other selector.

## 4. Syscall 547 — query_memory_protection, body RVA 0xaba540, narg 2

```
aba56d  mov r13,[rdi+8]       ; td_proc
aba571  and r14,[rsi]         ; uap[0x00] = va, masked ~0x3fff
aba574  mov rbx,[r13+0x200]   ; vmspace
aba57b  cmp r14,[rbx+0x28]    ; bound: va <= vmspace->vm_maxsaddr
aba57f  ja  0x8b47a6e5        ; else EINVAL 22
aba585  mov edi,8
aba591  call 0x8b4ebb00       ; privreader(8)
aba598  jne 0x8b47a6e5        ; NONZERO (we hold the bit) -> EINVAL
aba5a5  call 0x8ac86820       ; vm_map_lock
aba5b7  call 0x8ac86c40       ; vm_map_lookup(vmspace, va, &entry)
aba5c7  mov rax,[rsi+0x50]    ; entry->object
aba5d4  cmp byte [rax+0x9d],0xb ; object type must be 0xb
aba5dd  cmp byte [r13+0xc81],0
aba5e5  je  0x8b47a648        ; c81 == 0 -> non-PTE path
aba5e7  cmp dword [r13+0x5d8],0x6000000
aba5f2  jb  0x8b47a655        ; quota too small -> non-PTE path
aba607  call 0x8b47a710       ; PTE walk, r8d=1, out = &[rbp-0x78]
...
aba6ce  lea rdi,[rbp-0x90]    ; out struct
aba6d5  mov edx,0x18
aba6da  mov rsi,rbx           ; rbx = uap[0x08]
aba6dd  call 0x8ac191d0       ; copyout(0x18 bytes)
```

So the shape is `547(va, out_ptr)`, `out` is 0x18 bytes, and the privileged/PTE branch needs
**both** `proc+0xc81 != 0` **and** `proc+0x5d8 >= 0x6000000`. Section 3 shows a running process
cannot set c81, so on 14.10 the PTE path is unreachable from userland, and the non-PTE path
additionally needs `proc+0x5d4 > 0xfffffff`. What the non-PTE path returns is the **map entry's**
start/end and protection words, not a physical address.

`0x8b47a710` (RVA 0xaba710) is the PTE walk itself: it bzeroes a 0x48-byte struct at rcx, marks
bit 3 of byte [rcx+0x20], and calls 0x8b369270 with the pfn out-pointers. The masking constant
0xffffffffff000 lives inside that callee, not in the handler.

## 5. Status

| route | static verdict | live status |
|---|---|---|
| 547 PTE/physical-address leak | needs `proc+0xc81 != 0`; no userland writer exists | closed unless c81 is somehow set |
| 547 non-PTE | returns map-entry start/end/prot | worth one measurement, low value |
| 379 unbounded `va` | no bound check at all, unlike 547/572 | **open, one call away** |
| 379 as a c81 reader | does not work, both tables behave identically | closed here |

The one remaining live question in this file: what happens when 379 is handed a `va` above
`vmspace->vm_maxsaddr`. If vm_map_protect clamps, nothing. If it walks a map it does not bound,
it is a new surface.

## 6. Measured on 14.10, 2026-11-04 22:07 (probes 1204a and 1205a, one connection each, both COMPLETE)

### 6.1 547 returns map-entry metadata, so `proc+0xc81 == 0` for our process

```
547(va=0x310DD0000, out)  -> out+0x00 = 0000000310DC4000   (vma start)
                             out+0x08 = 0000000310DD4000   (vma end)
                             out+0x10 = 0061002000000003   (low dword 3 = RW, high 0x00610020)
547(va=0x310DD2C63, out)  -> identical, va is page-aligned down
```

That is the non-PTE branch: no physical address, no PTE, no kernel pointer. It also **proves the
c81 selector is 0 at runtime**, which is what section 3 predicted from the single writer at
0x38f7bf being inside process creation.

### 6.2 547's bound is the user-space ceiling, and it is enforced

| va | errno |
|---|---|
| 0x00007FFFFFFFF000 | EACCES 13 (bound passed, `vm_map_lookup` failed) |
| 0xFFFFFFFF8A9C0000 | **EINVAL 22** (the `cmp r14,[vmspace+0x28]` bound rejects it) |
| 0xFFFFFFFFFF600000 | EINVAL 22 |
| 0x0000000350EB4000 | EACCES 13 (in user range, not in our map) |

### 6.3 379 really has no bound check - and it still cannot act on a kernel address

`379(kernel_va, 0x1000, id=10, prot=3)` returns **EACCES 13, not EINVAL**, for every
out-of-range va tried (0x7ffffffff000, 0xffffffff8a9c0000, 0xffffffffff600000). The handler
therefore reaches `vm_map_protect` with a kernel address, which is the behaviour the missing
bound predicts. It is also the end of the road: `vm_map_protect` searches **our vmspace's**
map, the kernel range is not a VMA in it, and the call fails. No PTE is touched.

### 6.4 `id` is the one live selector, and it selects a protection policy

Only **id 10** gets past the gate at 0x8ad833e0; ids 0-9 and 11-15 answer EOPNOTSUPP 45 for every
prot. With id 10, the prot sweep on a page we own:

| prot | errno | | prot | errno |
|---|---|---|---|---|
| 0x00 | 45 | | 0x40 | 45 |
| 0x01 | 45 | | 0x80 | 13 |
| 0x02 | 13 | | 0x100 | 45 |
| 0x03 | 13 | | 0x400 | 13 |
| 0x04 | 13 | | 0x800 | 13 |
| 0x05 | 13 | | 0x1000 | 13 |
| 0x06 | 13 | | 0x8000 | 13 |
| 0x07 | 13 | | 0x10000 | 45 |
| 0x08 | 22 | | | |

Every value that reaches the map on a page we own comes back EACCES 13 - a protection-policy
refusal from the wrapper, not a successful mutation. The gate at 0x8ad833e0 is a policy check
keyed on the id, and the only id that exists for us refuses every prot the map would accept.

## 8. The id space, measured (probe 1206a, 2026-11-04 22:09)

`379(va, 0x1000, id, 3)` for every id in 0x00-0xFF, printed only when the errno changed:

| id range | errno |
|---|---|
| 0x00-0x09 | EOPNOTSUPP 45 |
| **0x0A** | **EACCES 13** |
| 0x0B-0x14 | EOPNOTSUPP 45 |
| **0x15** | **EINVAL 22** |
| 0x16-0xFF | EOPNOTSUPP 45 |
| 0x100-0x104 | EINVAL 22 |

Two boundaries, not one. The policy gate accepts an **8-bit id** and rejects anything >= 0x100 with
EINVAL - that is a real bound and it is enforced, so the id cannot be used as an out-of-range table
index. Inside 0..0xFF only 0x0A and 0x15 behave differently from EOPNOTSUPP, and neither of them
changes the mapping: `547` read back the same start, end and flags before and after the whole
sweep. 379 cannot alter a VMA on this firmware, which ends the last open question in this file.

The wrapper being called is a table lookup, not `vm_map_protect` directly: at RVA 0x3d144c the
callee does `movsxd rax,dword [rax+0x70] ; imul rbx,rax,0x138 ; lea rax,[rip+0x30ff9ee] ;
mov rdi,[rbx+rax+0x40]`, i.e. an object array with a 0x138-byte stride indexed by a dword field.
The id selects an entry in that array; it is not a raw protection mask.
